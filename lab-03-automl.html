Define the Evaluation Before Searching

Choose the target, metric, split strategy, and hyperparameter ranges before running the optimizer. For \(K\)-fold cross-validation on the development data, use

\[\widehat f(\lambda)=\frac{1}{K}\sum_{k=1}^{K} \mathcal L_{D_k}\!\left(A_\lambda(D_{-k})\right).\]

Fit scaling, imputation, feature selection, and resampling inside each training fold. Use group or temporal splits when the application requires them.

This notebook uses training, validation, and test partitions. Search and classroom comparisons use training/validation data; the final test cell is run only after decisions are frozen. Repeatedly choosing from test results would turn the test set into another validation set.

Hyperparameter Optimization

Parameters vs Hyperparameters

A learning algorithm \(A\) maps a training set to a model.

  • Parameters \(\theta\) are learned by \(A\) from data (e.g., regression coefficients, tree splits).
  • Hyperparameters \(\lambda\) are set before training and control how \(A\) learns (e.g., regularization strength, tree depth, learning rate).

We write \(A_\lambda\) for the algorithm instantiated with configuration \(\lambda\).

Algorithm Hyperparameter Domain
Logistic regression regularization strength C positive continuous, often searched on a log scale
Random forest number of trees, leaf size integer
Gradient boosting learning rate, leaf count, regularization mixed continuous and integer

Some choices activate others, so practical spaces can be conditional rather than simple Cartesian products.

The HPO Problem

Given training data \(D_{\mathrm{tr}}\), a learning algorithm \(A\), and a configuration space \(\Lambda = \Lambda_1 \times \dots \times \Lambda_n\), HPO solves

\[ \lambda^* \in \mathop{\arg\min}\limits_{\lambda \in \Lambda} f(\lambda), \qquad f(\lambda) = \mathcal{L}_{D_{\mathrm{val}}}\big(A_\lambda(D_{\mathrm{tr}})\big) \]

where \(\mathcal{L}\) is a validation loss (for ROC AUC we minimize \(1-\mathrm{AUC}\)). A low training loss alone does not identify the best hyperparameters.

\(f\) is a black-box function (Feurer and Hutter 2019):

  • no gradients and no closed form: we can only evaluate it;
  • each evaluation means training and validating a model, so it is expensive;
  • it is noisy (data splits, random seeds) and the space is mixed (continuous, integer, categorical) and often conditional.

HPO as an Optimizer–Learning-System Loop

The optimizer proposes a configuration; the learning system trains and validates it and returns a loss. Source: Hutter and Vanschoren AutoML tutorial.

The learning system fits model parameters; the optimizer changes hyperparameters. Sample efficiency asks how much validation improvement we obtain per expensive evaluation. Cost efficiency also accounts for unequal evaluation times.

Grid Search: Enumerate a Cartesian Product

Choose a finite set \(G_j\) for each of \(d\) hyperparameters. Grid search evaluates every point in

\[ G = G_1 \times \cdots \times G_d, \qquad N_{\mathrm{grid}} = \prod_{j=1}^{d} |G_j| \]

  • For a random forest, 4 depths × 3 leaf sizes × 5 tree counts means 60 candidates, or 300 fits with 5-fold CV, before any final refit. With \(m\) values per dimension, the count grows as \(m^d\).
  • Grid search is transparent, reproducible, and useful for small, carefully chosen spaces.
  • Its resolution is fixed by the grid: values between grid points are never tried, and adding an unimportant dimension still multiplies the work.
param_grid = {"classifier__C": [0.001, 1.0, 1000.0], "classifier__class_weight": [None, "balanced"]}
GridSearchCV(pipeline, param_grid, cv=5, scoring="roc_auc")  # 6 configurations, 30 fits

Random Search: Sample Configurations

Choose a sampling distribution \(p(\lambda)\), draw \(N\) independent candidates, evaluate each, and keep the one with the smallest validation loss:

\[ \lambda_1, \ldots, \lambda_N \sim p(\lambda), \qquad \widehat\lambda_N \in \mathop{\arg\min}\limits_{\lambda_i} \widehat f(\lambda_i) \]

  • Use categorical distributions for discrete choices and often log-uniform distributions for positive scale parameters. The distribution and bounds encode assumptions: a poor search space can defeat any optimizer.
  • The number of trials need not be a product of per-dimension resolutions; random search is easy to interrupt, extend, and parallelize (anytime).
  • It does not use earlier scores to propose later candidates.
param_distributions = {"classifier__C": loguniform(1e-3, 1e3), "classifier__class_weight": [None, "balanced"]}
RandomizedSearchCV(pipeline, param_distributions, n_iter=6, cv=5, scoring="roc_auc")

Why Random Search Works (1): Low Effective Dimensionality

Bergstra and Bengio (2012) showed that, for most datasets, only a few hyperparameters really matter, and which ones matter changes from dataset to dataset.

Nine grid points cover only three values of each coordinate; nine continuous random samples usually cover nine. Source: Bergstra and Bengio (2012) via the Hutter and Vanschoren tutorial.

If \(f(\lambda_1, \lambda_2) \approx g(\lambda_1)\), a \(3 \times 3\) grid spends nine trials on only three values of the important parameter; nine random samples typically explore nine distinct values. The advantage grows when a high-dimensional space has only a few influential dimensions.

Why Random Search Works (2): A Sampling Calculation

Let a useful region have probability mass \(p\) under the sampling distribution. With \(N\) independent trials:

\[ P(\text{at least one useful configuration in } N \text{ trials}) = 1 - (1-p)^N \]

Independent trials region of mass 5% region of mass 1%
20 64% 18%
60 95% 45%
300 >99.9% 95%
  • This is a sampling calculation, not a guarantee of generalization or of finding the global optimum.
  • The formula does not mention the dimension, but the mass of the useful region under \(p\) still depends on the space and its dimensionality.
  • Random search is a strong baseline: Li et al. (2018) include random search with twice the budget, which is competitive with several Bayesian optimization methods. Tiny useful regions, interactions, or informative adaptive proposals can change the comparison.

Demo: Grid vs Random on a Toy Function

The loss depends strongly on the first coordinate and weakly on the second. Compare a fixed nine-point grid with 1,000 repetitions of nine random trials. This deliberately constructed example illustrates low effective dimensionality: moving the optimum or changing the grid can change the outcome.

Code 
def toy_objective(l1, l2):
    """Validation loss: depends strongly on l1, weakly on l2. Minimum near l1=0.72."""
    return 1 - np.exp(-((l1 - 0.72) ** 2) / 0.02) + 0.05 * np.sin(6 * l2) ** 2

Beyond Random Search: Learning Where to Search

Random search ignores what it has already observed. Model-based and adaptive methods use the search history:

  • Bayesian optimization fits a surrogate to observed configuration/loss pairs and uses an acquisition function to balance exploring uncertain regions with exploiting promising ones (Snoek et al. 2012);
  • SMAC uses random-forest surrogates for algorithm configuration, including categorical and conditional choices (Hutter et al. 2011);
  • evolutionary and local-search approaches modify good candidate configurations.

All of them still face the same fundamental limit: every evaluation costs resources.

The Budget Problem

The Budget Is Part of the Problem

A trial budget limits the number of candidates. A time budget limits elapsed time. They differ: a deep forest can cost much more than a small linear model. Include CV folds, preprocessing, search overhead, and final refitting when reporting total cost.

For a sequential search history \(H_N = \{(\lambda_i, r_i, \widehat f_i, c_i)\}_{i=1}^N\), a simplified resource constraint is

\[ \sum_{i=1}^{N} c(\lambda_i, r_i) + c_{\mathrm{overhead}} + c_{\mathrm{refit}} \le B \]

where \(r_i\) is the fidelity (e.g., sample size or epochs), \(c\) the cost, and \(B\) the total budget. The cost depends on the configuration (500 trees cost more than 5), so \(N\) is not fixed. The optimizer chooses what to evaluate, at what fidelity, and when to stop; it returns the best observed candidate, not a certified global optimum.

Compare methods with the same data, metric, hardware, and resource accounting. Report the requested budget and the measured elapsed time: a library time limit is not a hard operating-system deadline.

Anytime Performance Under a Budget

For completed trials with validation losses \(f_i\) and completion times \(t_i\), define the incumbent curve

\[f^*(\tau)=\min\{f_i:t_i\le\tau\},\qquad \tau\le B.\]

Before the first completed trial there is no incumbent. With a fixed evaluation protocol, the best observed loss cannot increase as trials finish. Plotting this curve against elapsed time reveals how quickly an optimizer becomes useful; plotting against trial count answers a different question.

Budget can also mean CPU/GPU hours, money, or energy. Wall-clock time depends on hardware and parallelism, so report the execution setting along with the curve.

Spending the Budget: Adaptation and Fidelity

Adaptive search uses previous evaluations to choose later candidates. Multi-fidelity search first uses cheaper approximations \(f(\lambda, r) \approx f(\lambda)\) and then spends more resources on promising candidates.

Low fidelity Higher fidelity
fewer rows more rows
fewer trees / boosting rounds more trees / rounds
fewer epochs more epochs

SVM validation error at increasing MNIST sample sizes: the good region is already visible on small subsets. Source: Hutter and Vanschoren tutorial.

Low fidelity is useful when it preserves enough of the high-fidelity ranking; it can also discard slow-starting or data-hungry models.

Successive Halving, Hyperband, and BOHB

Successive halving (Jamieson and Talwalkar 2016) repeatedly removes weak candidates while increasing resources for survivors. With reduction factor 3:

Round Candidates Resource per candidate Total resource
0 27 1 unit 27 units
1 9 3 units 27 units
2 3 9 units 27 units
3 1 27 units 27 units
  • Hyperband (Li et al. 2018) varies the initial breadth/resource trade-off across halving brackets to hedge against misleading low fidelities.
  • BOHB (Falkner et al. 2018) combines model-based configuration sampling with Hyperband-style allocation.
  • Constant work per round is an idealization: training cost need not grow linearly with resource, and implementations may refit promoted candidates.

Combining Ideas: BOHB

Regret against wall-clock time in the BOHB experiments: Hyperband (HB) gives strong anytime performance, Bayesian optimization (TPE) strong final performance, BOHB both. Source: Falkner et al. (2018) via the Hutter and Vanschoren tutorial.

AutoML

What Is AutoML?

Automated Machine Learning (AutoML) automates choices in constructing and evaluating an ML solution, within a user-defined task, search space, metric, and budget (Hutter et al. 2019). Depending on the system, these choices include preprocessing, features, learning algorithms, hyperparameters, and ensembles.

Part Meaning in this lab
Task Dataset, target, and evaluation goal
Learning system A candidate tabular ML pipeline
Optimizer Algorithm selection and hyperparameter search
Budget The time allowed for candidate evaluations

HPO fixes the learning algorithm and tunes its settings. AutoML can also choose the algorithm and parts of the pipeline. Humans still define success, admissible data, evaluation design, and operational constraints.

The CASH Problem

Combined Algorithm Selection and Hyperparameter optimization (Thornton et al. 2013). Let \(\mathcal{A} = \{A^{(1)}, \dots, A^{(k)}\}\) be candidate algorithms, each with its own configuration space \(\Lambda^{(j)}\):

\[ A^{*}_{\lambda^{*}} \in \mathop{\arg\min}\limits_{A^{(j)} \in \mathcal{A},\; \lambda \in \Lambda^{(j)}} \; \frac{1}{K} \sum_{i=1}^{K} \mathcal{L}\big(A^{(j)}_{\lambda}, D^{(i)}_{train}, D^{(i)}_{valid}\big) \]

Its domain is a conditional union \(\bigcup_j \{A^{(j)}\} \times \Lambda^{(j)}\), which can be rewritten as a single HPO problem with a root hyperparameter \(\lambda_r \in \{A^{(1)}, \dots, A^{(k)}\}\): \(\Lambda^{(j)}\) is active only if \(\lambda_r = A^{(j)}\). A practical solver approximates this objective under a resource budget.

CASH is the algorithm-selection problem; computation caching is a separate implementation technique.

CASH Search Spaces Are Conditional

If the optimizer chooses… It may tune…
random_forest tree depth, number of trees, leaf size
logistic_regression regularization type and strength
gradient_boosting learning rate, estimators, tree constraints
  • The space is a tree, not a rectangle: a grid over the union of all hyperparameters would be meaningless.
  • Algorithms have very different costs: a linear model trains in milliseconds, a 1000-tree ensemble in minutes.
  • So CASH inherits all the HPO difficulties and the budget problem becomes central: which algorithm deserves the next unit of budget?

auto-sklearn: Pipeline Search, Meta-Learning, and Ensembles

auto-sklearn (Feurer et al. 2015) solves CASH over scikit-learn pipelines:

  • Search space: a fixed template (data preprocessing → feature preprocessing → classifier) with 15 classifiers, 14 feature preprocessors, and 4 data preprocessors (110 hyperparameters).
  • Optimizer: SMAC proposes conditional configurations (Hutter et al. 2011).
  • Meta-learning: warm-starts the search with configurations that worked on similar datasets.
  • Ensembling: builds an ensemble from the models evaluated during the search.

auto-sklearn 2.0 (Feurer et al. 2022) adds a portfolio of initial configurations, successive-halving allocation, and learned selection of model-selection policies. These are version-specific design choices, not capabilities of every AutoML system.

FLAML: What Makes Search Economical?

FLAML (Wang, Wu, Weimer, et al. 2021) targets low computational cost: good models under small budgets.

  • Cost-aware learner selection: chooses which learner to try next from the cost and expected benefit of further search.
  • Cost-frugal hyperparameter search: CFO (Wu et al. 2021) runs randomized local search starting from low-cost initial configurations; BlendSearch (Wang, Wu, Huang, et al. 2021) blends local and global search.
  • Sample size as fidelity: early trials can run on a subsample that grows over time.
  • FLAML uses its own cost-aware search and resource allocation; it should not be described as simply running Hyperband.

Search and resampling behavior depend on configuration and version: this lab explicitly fixes the holdout split and the learner lists.

auto-sklearn vs FLAML

def describe_space(space):
    rows = []
    for name, spec in space.items():
        domain = spec["domain"]
        if hasattr(domain, "categories"):
            values = str(list(domain.categories))
        elif hasattr(domain, "lower") and hasattr(domain, "upper"):
            sampler = domain.get_sampler() if hasattr(domain, "get_sampler") else None
            values = f"[{domain.lower}, {domain.upper}] ({type(sampler).__name__})"
        else:
            values = str(domain)
        rows.append({"hyperparameter": name, "domain": values,
                     "init_value": spec.get("init_value"),
                     "low_cost_init_value": spec.get("low_cost_init_value")})
    return pd.DataFrame(rows)

End-to-End Pipeline Optimization

From CASH to End-to-End Pipeline Optimization

So far we fixed data cleaning, category encoding, feature availability, and validation design, then searched over learners. End-to-end pipeline optimization also searches over the structure and operations that turn raw data into predictions.

Let \(s\) denote a pipeline structure, \(\theta \in \Theta_s\) its conditional settings (operators and hyperparameters), and \(\mathcal{S}(C)\) the structures allowed by human constraints \(C\):

\[ (s^*, \theta^*) \in \mathop{\arg\min}\limits_{s \in \mathcal{S}(C),\; \theta \in \Theta_s} \widehat{\mathcal{L}}_{\mathrm{val}}\big(\mathrm{Fit}(P_{s,\theta}, D_{\mathrm{tr}})\big), \qquad c_{\mathrm{search}} \le B \]

A pipeline may chain imputation → encoding → feature construction/selection → resampling → learner → calibration. Structure can be a sequence or a graph; changing an early step changes the meaning and cost of later choices.

Why Full Pipeline Search Is Harder

  • Combinatorial explosion: allowing each of \(s\) step types at most once gives \(\sum_{m=0}^{s} s!/(s-m)!\) ordered structures, 326 for \(s=5\), before choosing operators and hyperparameters (constraints remove many of them).
  • Dependencies and order: scaling matters for some learners (before a tree it is often unnecessary rather than invalid); SMOTE must follow a suitable representation and stay inside training folds; the order of transformations changes results (Giovanelli et al. 2021).
  • Data quality: deletion, imputation, and feature construction change who is represented and what the model learns.
  • Constraints: accuracy competes with latency, fairness, interpretability, and resources; some pipelines are inadmissible even if accurate.
  • Evaluation: more trials increase validation overfitting; learned transformations must be refitted inside each training split.
  • Control and provenance: record data versions, transformations, constraints, code, and failures so humans can understand and revise a result.

auto-sklearn fixes the structure; TPOT (Olson et al. 2016) explores pipeline structures with genetic programming. Augmentation (lab 1) and feature selection (lab 2) can become pipeline choices.

HAMLET: Human Knowledge Shapes the Search

HAMLET (Francia et al. 2023) makes AutoML an iterative, human-in-the-loop process grounded in structured argumentation (author repository).

  • Knowledge as rules: the data scientist encodes constraints in a logic-based language: data constraints (forbidden features), ordering constraints (which preprocessing step may follow another), learner requirements (e.g., normalization for distance-based methods).
  • Argumentation: possibly conflicting rules form an argumentation theory, represented through a Problem Graph, whose accepted conclusions define the search space.
  • Exploration and insights: AutoML explores the constrained space; the explored configurations are mined to recommend new rules back to the user.
  • Iteration: encode rules → derive an admissible space → search → inspect evidence → revise rules.

The question shifts from “Which model won?” to “Which alternatives were allowed, and why?”

Discussion: distinguish a hard admissibility constraint from a preference that can trade off against predictive performance.

MLZero: Agents Build and Repair ML Workflows

MLZero (Fang et al. 2025) uses LLM agents to go from raw data to a working ML solution with minimal human input.

  • Perception module: turns raw, multimodal inputs into a structured description of the task.
  • Multi-agent workflow: agents plan, write code, execute, and debug iteratively.
  • Memory: semantic memory (library knowledge) and episodic memory (past attempts and errors) reduce hallucinated or outdated API calls.
  • Results: strong performance on MLE-Bench Lite and on a 25-task multimodal AutoML agent benchmark, also with a compact 8B LLM. Benchmark results do not establish reliability on every deployment task.

The action space is no longer a prewritten configuration space: agents generate and revise executable workflows.

Discussion: if an agent writes preprocessing code for Adult Income, which execution checks and independent validation would detect leakage, invalid assumptions, or an apparently successful but wrong solution?

AGE-ML: Specifications for Data-Centric AutoML

AGE-ML (Matteini et al. 2026) observes that AutoML focuses on model selection and HPO, while its decisions on preprocessing, pipeline structure, and validation are hard to inspect or modify, which clashes with MLOps practice.

  • The data scientist writes a human-readable specification: assumptions, constraints, evaluation criteria, design preferences.
  • The system derives a search space from the specification and explores it in a controlled, reproducible way.
  • LLMs act inside a constrained agent loop: they interpret the specification, generate and validate pipelines, and explain them, with experiment tracking.

The conference abstract does not give enough detail to reproduce experiments or infer numerical improvements; use it as an architectural reference.

Discussion: write a specification for our classification task: target, permitted features, missing-value policy, split protocol, objective, budget, and explanation requirements. Which parts could a validator check automatically?

Compare the Boundaries of Automation

Approach What can change? What should the human inspect?
HPO Hyperparameters of a fixed learner Bounds, sampling distributions, evaluation
CASH / our FLAML example Learner and its hyperparameters Learner list, budget allocation, selected configuration
Full pipeline search Preprocessing, features, structure, learner Leakage, admissible operations, constraints
HAMLET Search space derived from knowledge and argumentation Rules, Problem Graph, revisions
MLZero Agent-generated and iteratively repaired workflows Generated code, execution evidence, validation
AGE-ML Pipelines generated from explicit specifications Specification compliance, provenance, explanations

This compares scope, not performance. Risks differ too: fixed spaces can exclude useful solutions; rule-based systems need knowledge engineering; code-generating agents need execution checks; specification-driven systems depend on the quality of the specification.

Discussion: which evidence and human controls would you require in a lending application? (Adult Income is an income-prediction dataset, not a creditworthiness label.)

Demo: Human Constraints Shape an Executable Search

Turn a small human-readable specification into a feature filter and FLAML settings. Compare a reference specification with an otherwise identical one that forbids sex, race, and native_country: same F1 metric, learner list, budget, seed, and validation partition, so the intended changed factor is feature admissibility (time-limited searches can still follow different paths).

This illustrates applying a specification; it is not an implementation of HAMLET or of an LLM agent. Removing attributes does not guarantee fairness: proxies and unequal error rates can remain (see the fairness lab).

Wrap-Up

What AutoML Automates (and What It Does Not)

AutoML can automate repetitive parts of modeling:

  • trying candidate learners and allocating trials under a budget;
  • tuning hyperparameters;
  • returning a strong, reproducible baseline.

AutoML does not remove the data-science responsibility for:

  • problem formulation and target definition;
  • leakage checks and validation design;
  • fairness assessment and deployment monitoring;
  • deciding whether a model should be used at all.

A good AutoML report explains both the machine-selected model and the human choices that shaped the search.
